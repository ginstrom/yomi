# Sprites (sprite-tool)

Guidance for working in `art/`, the text sources of every sprite in the game. The root `CLAUDE.md` covers the rest of the project. Commands here are run from the repository root.

Sprites are made with [sprite-tool](https://github.com/ginstrom/sprite-tool) (`uv tool install git+https://github.com/ginstrom/sprite-tool@v0.6.0`; add `--force` to upgrade a copy already installed), which is installed on the host and is not in the podman image. Run `sprite guide --project art` before drawing or changing one: it prints the file format, the palette and the canvas classes.

- Sources are text in `art/**/<id>.sprite.toml`; `art/sprite-tool.toml` holds the canvas classes and the export target. Create one with `sprite new <kind> --canvas unit --project art --dir units`, where the id is the `UnitKind` (and so the name the atlas shows it by), or with `sprite new icon_<id> --canvas icon --project art --dir icons --runs` for a sprite started as runs.
- A frame is written as a grid, one character per pixel, or as runs: `[frames.<name>.runs]`, then one line per row that has pixels, each a list of `[column, "pixels"]`. Runs suit a sprite that is mostly empty, which is most of them on the 32px canvases. With `outline = "auto"` at the top of the file, draw only the interior and the tool adds the `k` outline. Do not write a script to generate a grid: placing pixels at a row and column is what runs do.
- An item that differs from another only in colour is a `[variants.<name>]` table in that icon's file (`swap = { <key> = "<key>" }`, built as `<id>_<name>.png`), not a new file.
- Loop: `sprite check --project art` until it prints `ok`; `sprite show <id> --project art` to read the result as text, outline included; `sprite preview <id> --grid --project art` for the colours, looking at the PNG it names; then `npm run sprites`.
- The build has two targets, both into `public/assets/sprites/`. `frames` writes loose PNGs (`<id>.png`, the first frame, and `<id>__<frame>.png` for each frame of a sprite with several), of which the scenes load the icons and the portraits, plus `sprites.json`, a per-sprite metadata index (size, anchor, bounds, display scale) that nothing loads yet. `phaser` writes `atlas.png`, `atlas.json` and `atlas.anims.json`: every frame on one sheet, and every `[anim.<name>]` as a Phaser animation called `<id>/<name>`. `BootScene` loads those, and units, gear and the map's sprites are shown from them. Neither target says which sprites it exports (since 0.5.0 one could, with `canvases`, `include` or `exclude`), so the loose PNGs of the atlas's sprites are written and committed though nothing loads them. Commit everything the build writes, `.sprite-tool-manifest.json` included, with the source; never edit an exported file by hand.
- Movement is frames and an `[anim.<name>]` in the sprite's own file; the scenes only say which animation plays. A unit has `idle` (`idle_0`, and `idle_1` with everything above the shins a pixel lower) and `walk` (`walk_0`, the legs apart; `walk_1`, the left foot lifted; `walk_0` again; `walk_2`, the right foot lifted: four beats that change only the leg rows, so gear keeps to its `idle_0`); a map sprite has `idle` over its `base` frame. A frame that changes a few pixels is derived (`from`, then `rows` or `runs`); `idle_1` is a whole grid, or derived with `move`, which takes the rows above the shins a pixel down (`units/shaman`, `rows = [0, 23]`, whose staff runs below them; `units/warrior`, `rows = [0, 24]`, knees included). `sprite show <id> --frame <name> --diff` prints only the rows a frame changes from the one it is derived from.
- A hero is drawn in layers: `units/warrior` is the body with empty hands, and each thing a hand can hold is a sprite of its own in `gear/` (`gear_<icon>`, on the `unit` canvas so it lines up, with a `[variants]` table for an enchanted one), laid over the body by `GEAR_SPRITES` in `src/scenes/unitLook.ts`. A weapon is gripped at column 25: the fist is at rows 18 to 20, columns 22 to 27, and the weapon leaves row 19 open for the hand to show through. The warrior names that pixel `[points] grip = [25, 19]`, which the atlas exports on every frame (sinking a pixel in `idle_1`, as `move` carries it) and `UnitFigure.swing` turns the weapon about, so moving the fist means moving the point, not code. A gear sprite says `over = "warrior"`: the outline rule is checked against the body beneath it (the bow's string, one pixel wide, is `unoutlined`), its `[anim.idle]` is `like = "warrior"`, and its `[anim.walk]` is `rest = true`, holding `idle_0` while the body walks; `check` warns (W009) of a body animation a gear sprite neither plays nor rests through. Its `idle_1` is `idle_0` shifted down a pixel, so the two breathe together. `sprite preview gear_<icon> --on warrior --project art` shows one over the body.
- The tool only overwrites files listed in the manifest, and every PNG in `public/assets/sprites/` is now on it. A PNG put there by hand stops the build for a sprite with the same id; replacing one deliberately takes a one-off `sprite build --adopt --project art`, plus an update to the sprites `README.md`.
- All sprites share `palette.toml`, a muted Baldur's Gate-style palette. Units are drawn on the 32px `unit` canvas and shown at 3x, so creature size is drawn into the sprite; item icons use the 20px `icon` canvas at 2x, and the world map's points of interest (`map/map_<kind>.sprite.toml`, one per `LocationKind`, `map_watchtower`, and `map_blight`, which is shown at 1x inside a corrupted hex) use the 24px `map` canvas at 2x. The encampment screen's facilities (`encampment/camp_<facility>.sprite.toml`, a frame `level_<n>` for each level, and `camp_plot` for one not built) use the 48px `building` canvas at 3x, and its tent and campfire the `map` canvas. Portraits (`portraits/portrait_<id>.sprite.toml`, one per `PortraitId` in `src/character/portraits.ts`) use the 32px `portrait` canvas at 2x in the party's column and 4x on the character panel; it has no outline rule, as a portrait fills its canvas edge to edge: a head and shoulders facing the viewer, outlined in `k`, over a dark ground with a lighter disc behind the head.
- `art/units/warrior.sprite.toml.example` is the tool's sample sprite, renamed so it is not built. It is a format reference, not the game's warrior.

When a canvas class, a sprite directory or a step of this workflow changes, update this file in the same commit.
