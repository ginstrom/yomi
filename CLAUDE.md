# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Yomi is a 2D turn-based fantasy tactics game: Phaser 4 + TypeScript, bundled with Vite. Battles are fought on a pointy-top hex grid, with action points, flanking, facing arcs and zones of control. Between battles the party travels a world map, also of hexes, from one point of interest to the next.

## Commands

Node 26+ is required: `scripts/*.ts` run on Node's native TypeScript support (no build step, no ts-node), and imports use explicit `.ts` extensions everywhere.

| Task | Command |
| --- | --- |
| Dev server (http://localhost:5173) | `npm run dev` |
| Typecheck only | `npm run typecheck` |
| Typecheck + all tests | `npm test` (`tsc && vitest run`) |
| One test file | `npx vitest run src/grid/hex.test.ts` |
| One test by name | `npx vitest run src/engine/battleEngine.test.ts -t "routes around zones"` |
| One vitest project | `npx vitest run --project domain` (or `scenes`) |
| In-browser tests (headless Chromium) | `npm run test:browser` |
| One in-browser test by name | `npm run test:browser -- -t "victorious"` |
| Retake the player's manual's screenshots (`docs/manual/`) | `npm run manual:screenshots` |
| Production build | `npm run build` |
| Headless battle simulator | `npm run simulate -- --battles 2000 --seed 1` |
| Build sprites from `art/` | `npm run sprites` |
| Check exported sprites are up to date | `npm run sprites:check` |

There is no linter; `tsc` is the lint step (`noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`, `verbatimModuleSyntax`). `erasableSyntaxOnly` means no enums, namespaces or constructor parameter properties; use `import type` for type-only imports.

The `Makefile` runs the same things inside a podman container (`make run`, `make test`, `make test-browser ARGS="-t victorious"`, `make simulate ARGS="..."`, `make shell`), with `node_modules` in a named volume that reinstalls itself when `package-lock.json` changes. `vite.config.ts` polls for file changes because of that bind mount.

Simulator flags: `--battles`, `--seed`, `--out` (default `logs/battles.jsonl`; `logs/` is gitignored), `--max-rounds`, `--player-policy`, `--enemy-policy` (`aggressive` or `random`), `--player-weapon` (the id of any weapon `itemById` builds, of any family and tier, enchanted, graded or modified, e.g. `yew_bow`, `steel_war_hammer`, `iron_spear`, `iron_sword@2`, `iron_sword+light1` or, runed, `'iron_sword@3#ember1'` (quoted, so that no shell reads the `#`), put in every party member's hand; the way to compare weapon balance, between weapons of one skill, as the heroes are not all trained in the same), `--encounter` (an id from `ENCOUNTERS`, default `goblin_raid`), `--threat` (how dangerous to make it, default 1) and `--party-level` (the level every member is raised to, at full hit points and with its skill points and perks spent by `autoAdvance`, default 1); the last three check one cell of scaling. `--ready-level` (campaign only) is the level every member must reach before the party marches on the Source, default `SOURCE_READY_LEVEL` (7). The player's side is the ready-made party (`readyMadeParty`). It writes every event as JSONL and prints a summary of win rate, rounds, hit rates, free attacks, spells cast, area attacks used, hit points healed (a drain's included) and statuses laid by each side (a spell's and an area attack's damage count in the damage dealt of the user's side, and a status's damage at a turn's start in the damage of the side whose foe it hurt; the hit and critical rates are of weapon attacks).

`--campaign` makes each of `--battles` a whole campaign, which is how scaling is judged: a new ready-made party sets out on a new world (seeded from the campaign's seed) with the blight spreading, and walks a day a hex to where `nextTarget` sends it: the nest pushing hardest on a held site under threat, else the nearest nest whose threat is no higher than its lowest level, and the Source once every member has the ready level (`--ready-level`, by default `SOURCE_READY_LEVEL`, 7) or nothing else is left. It fights each at its own threat, carrying its hit points and the mana its casters have left, taking `rewardVictory` after each win, spending it with `autoAdvance` and camping where it won until healed (`campUntilHealed`, again whenever an event breaks camp), until the Source is beaten, a battle is not won, the encampment falls or `MAX_CAMPAIGN_DAYS` pass. Item loot is not used; rune loot is, taken after each win (`takeRunes`, from the seed the battle was fought with). It refuses `--encounter`, `--threat` and `--party-level`, tags each `battle_start` with `meta.campaign`, `meta.location` and `meta.day`, builds a watchtower wherever it stops after a win if the land and the stock allow, then an outpost on the nearest held site without one within `OUTPOST_ERRAND_RADIUS` (6) if the stock allows (`outpostErrand`), goes home to the guild hall when the stock affords its next level and no held site is threatened or affords a recruit for an empty place (`hallErrand`), where it raises the hall as far as it can and fills the party with pre-rolls, renamed when taken, spent by `autoAdvance` (`visitGuildHall`), then sells the baggage and the materials beyond what it still means to buy (`materialNeeds`), raises the trading post, workshop and infirmary as the stock allows, buys each member, for its weapon, shield and armour, the dearest item of the same family the post sells (tier 2 from level 4) that the gold affords and costs more than what is worn (extracting the old item's runes first where the workshop may, else selling them with it), then at a workshop only fuses every Lesser triple, buys Lesser runes for the empty sockets the pouch cannot fill and embeds by `RUNE_ORDER` (weapons Ember, Storm, Stone; shields and armour Stone, Life; a kind's highest rank first) (`runecraftGear`), crafts on them by `PREFERRED_MODIFIERS` (`craftGear`) and raises the shrine with what is left (`visitFacilities`); after each win it also field-crafts one piece of gear if the stock allows, a day; and it prints how the campaigns ended (the Source beaten, the party fallen, the encampment lost, out of days), the days, battles, spawns, sites captured and lost and the land blighted at the end, the watchtowers built and lost, the shrine's level at the end and the outposts built, the trading post's, workshop's and infirmary's levels at the end, the gold spent on gear, the tier-2 items bought and the gold taken from sales and the items crafted (and the field crafts' days), the runes found, bought and fused, the gold on runes and the sockets filled at the end, the hall's level at the end, the recruits and the heroes dead, the hit points healed between battles and the days camped for them, the party's lowest and highest level at the end (the fallen party's, for a campaign lost in battle), the levels heroes died at, the battles it took the party's lowest level to reach 5, 10, 15 and 20 and how many campaigns did, and the battles won at each threat: `npm run simulate -- --campaign --battles 500 --seed 1` (about a minute, and a log of some 70 MB).

In dev builds `~` (or `` ` ``) opens a debug console over the top of the game (`debugConsole.ts`, plain HTML as the manual is, taking every key while open; `help` lists the commands, which live in `debugCommands.ts`). It works on the `DebugSource` of the scene in front (`debugSource()`, which `World` and `Battle` have): anything reads, but a command that changes the game (healing, experience, stock, items, facilities' levels, revealing the map, moving the party, passing days, starting a battle of any encounter at any threat (`fight`, through the source's `fight`, which only `World` offers)) runs only on the world map, which redraws and saves after it, as a battle's engine would never hear of the change. A new command is an entry in `COMMANDS` there. `give <item|rune> [count]` puts items in the baggage or, given a rune key (`storm1`), runes in the pouch; `items` lists the item ids, the rune keys and the `#` grammar, and `runes` lists the pouch. A battle `fight` starts has no location behind it: `Battle` is started with `encounter` and `threat` in its data instead (`chooseBattle`, used only without a `location`), and a win gives experience but clears no location, takes no loot and rolls no runes, leaves the blight alone and is never saved mid-battle.

The game takes a seed from the page's address, as in `http://localhost:5173/?seed=42` (`seed.ts`; `main.ts` puts it in the game's registry). Every battle of that session is then fought with it, the enemy's choices included, so the same actions play out the same way: use it to replay a battle from the seed its `battle_start` logged. Without one each battle draws a seed of its own, which its `battle_start` logs all the same.

## Committing

Commit finished work without being asked: once a change is complete and `npm test` passes, commit it on the current branch. Commits are free in this project's workflow, so there is no need to wait for a go-ahead. Do not push unless asked.

## Subagents

When spawning an agent, pick its model by the task. Pass `model: "sonnet"` for work that is not too complex: searching the code or finding where something lives, reading and summarising files or logs, running the tests or the simulator and reporting the result, and mechanical edits whose shape is already decided (a rename, a table entry, a doc update). Leave the model unset, so the agent inherits the session's, for work that needs judgement: designing or planning a feature, changing the engine's rules or the balance, debugging a failure whose cause is unknown, and reviewing code. When in doubt between the two, use the session's model.

## Architecture

The central rule: **game rules are Phaser-free and live outside the scenes.** The same `BattleEngine` drives the in-browser game and the headless simulator, so anything that changes a battle's outcome has to go in the domain modules, with tests.

### Domain layer (plain TypeScript, runs in Node)

- `src/grid/hex.ts`: axial `{q, r}` hex maths, odd-r offset conversion for the rectangular board, `HEX_DIRECTIONS` (opposite directions are 3 apart), `areaOf` (the hexes of an area's shape, `AreaShape` burst, cone or line, from an origin towards an aim) and `reachableHexes`, the pathfinder that prefers routes provoking the fewest distinct foes.
- `src/combat/`: percentile attack resolution (a roll of 1 to 100 hits when within the attacker's `toHit`, plus bonuses, less the defender's armour class, the chance kept between 5 and 95; a hit is critical when the roll is also within `critChance`), damage rolls and what a weapon hit does through the defender's `resistance` (`damageThrough`, `effectiveResistance`), monster stat blocks and what a level adds to them (`foeAtLevel(base, level, native)`, from the kind's native level: a level below it counts as it, armour class, chance to hit, damage (its abilities' too, as `abilityDamageBonus`) and a caster's mana and skill grow by the levels above it, and hit points are scaled so that a block is as written at its native level and grows as a level 1 block would from there), the yardstick a foe of a level should sit in (`foeYardstick`: armour class, chance to hit, hit points and mean damage a turn (the better of its weapon's turn and a routine's), from the ready-made fighter's measured growth, which a test in `encounters.test.ts` holds every monster kind to at its native level, each field outside it a named exception), the spells as the engine casts them (`SPELLS` in `spells.ts`: school, cost, what it is aimed at, range and area, whether it is hostile, its damage and its element, healing, drain or status; and `STATUSES`, what each lasting effect does; nothing of the perk that teaches a spell; `SPELL_IDS` are the heroes' spells, `HeroSpellId`, which perks, the spell tree and casting on the world map alone read, and `MONSTER_SPELL_IDS` the spells only a stat block's `magic` can name (Lightning Bolt, Drain Life, Curse, Web, Dark Shield), `ALL_SPELL_IDS` both in that order), the elements (`ELEMENTS`: fire, frost, lightning, acid, poison, blight) and a stat block's `wards` against them, flat points off each instance of damage of the element (`warded`), the abilities (`ABILITIES` in `abilities.ts`, by id as spells are, which a stat block's `abilities` names: a routine of weapon strikes at one foe, each with its own dice, verb and maybe a status, or an area; each costs action points and no mana, and one with a `recharge` of N is used at most every N turns of its side; heroes have none), and the seedable `mulberry32` RNG, which can tell where its stream stands (`state()`) so that a saved battle rolls on as the unsaved one would. A stat block's optional `magic` (mana, spell skill, spells known) is what makes a unit a caster; without it a unit behaves as it always did.
- `src/character/` and `src/inventory/`: a persistent `Character` and its equipment. A character stores only what it was born with (`attributes`, `tagged` skills), what it has learned (`level`, `trained` skill points, `perks`), what it has left (`hp`, and `mana`, read through `manaOf`) and what it carries; every number it fights with is derived from those, never stored: `maxHp`, `maxMana`, and `deriveCombatStats`, which turns a character into the `CombatantStats` the engine fights with. That holds for attributes too: `character.attributes` is what it was born with, and every reader goes through `attributeLevel` (`perks.ts`), which adds what its perks have raised. `attributes.ts`, `skills.ts` and `perks.ts` are the three tables, with the rules for raising a skill and qualifying for a perk; `skills.ts` and `perks.ts` import each other, which is safe only while neither calls the other as its module loads. `creation.ts` is character creation: a `CharacterDraft` is what the player chose (attributes, tag, skill points placed, perks in the order taken, name, portrait) and `draftCharacter` the level 1 `Character` it makes; the screens call its functions and decide nothing. `catalog.ts` is the catalog of plain gear: the families (`FAMILIES`, 28: weapons, shields, body armour and the head, gloves and boots slots, each with its slot, material kind, icon and tier-1 stats, among them what it asks of strength (`strength`) and takes in action points (`apPenalty`), a reach weapon's `reach` and the crossbow's `rangedPierce`, which `deriveCombatStats` derives (see the rules of characters)), the materials (`MATERIALS`, a tier 1 and a tier 2 of each kind: iron and steel, yew and ironwood, leather and wolfhide, linen and silk), what tier 2 adds by gear class (`TIER_BONUS`, `gearClass`: weapon, shield, armour, small) and the legacy ids (`LEGACY_ALIASES`). `inventory.ts` has the items: the plain items the trading post and crafting work with (`BASE_ITEMS`, generated as every family in each material of its kind, tier 1 first: 56, the Wand of Sparks among them as the wand's tier 1), the six plain weapons a new hero carries (`WEAPONS`) and the enchanted ones won as loot (`MAGIC_ITEMS`). A plain item's id is `<material>_<family>` (`steel_longsword`), or for a tier 1 that has its own the family's `tier1` id (`iron_sword`, `oak_shield`, `spark_wand`, `ash_staff`, `leather_armor`); the tier-1 greatsword and breastplate are `iron_greatsword` and `iron_breastplate`, `steel_greatsword` being tier 2's and `steel_armor` an alias of `iron_breastplate`, which builds the same object, carrying the canonical id. A plain item comes in three grades (`grades.ts`) and may carry one modifier (`modifiers.ts`, `MODIFIERS`: the families it fits, the workshop level that unlocks it, its stat change at each grade); such an item is named by its id, `<plain>[@<grade>][+<modifier><grade>][#<rune>(.<rune>)*]` (`iron_sword@2+light1`, `steel_longsword@3#ember2.storm1`; grade 1 is never written, so each item has one id; an enchanted item takes the `#` part only, `emberblade#dawn1`), and `itemById` builds it from that id and remembers it, so one id is always one object, refusing an id with more runes than the item's sockets or a rune that does not fit (`runeFits`: Mind in a weapon only if it strikes with Magic, Acid only if it is a melee weapon or the crossbow, whose piercing it adds to; `runeFitsOnly` says where the rune fits, for the refusal). Every plain item, graded, modified or runed, carries its `family`, `material` and `tier`, and a runed plain item gets `base` and any runed item its `runes` (in socket order, filled sockets first; `unruned`, `withRunes`, and `craftedItem`, which keeps them). A grade adds by gear class (damage to a weapon, armour class to a shield or a small-slot item, resistance to body armour) and never changes attack AP, range, piercing, strength or a penalty; no tier, grade or modifier touches maximum hit points (a Life rune does, see `clampHp`); enchanted items take no grade or modifier. `runes.ts` has the runes: ten kinds (`RUNES`) at four ranks, each doing one thing in a weapon (the main hand), another in armour (every other slot) and another in a shield (`slotClass`), folded into a runed item's stats (`addStats`); the sockets (`socketsOf`: 0 at tier 1 and 1 at tier 2, one more at Masterwork, at most 3, a small-slot item at most 1, and the Emberblade, the Wand of Storms and the Hawkeye Bow 1 of their own); the pouch's helpers, and the one phrasing of on-hit effects (`onHitParts`, long, or short for the character panel's narrow column), which every screen that tells them uses. A rune adds the `ItemStats` fields `wards` (by element), `onHit` (a weapon's flat on-hit damage, status or healing, `OnHit` in `combat.ts`) and `maxHp`, besides the old ones, which `deriveCombatStats` and `maxHp` derive (wards summed over everything worn, `onHit` from the main hand only, the worn items' `maxHp` added) and the engine resolves. `portraits.ts` lists the preset faces (`PORTRAIT_IDS`); a character's `portrait` is only looks. See the rules of characters below.
- `src/character/progression.ts`: levels and experience: what each level costs (`xpToNextLevel`), what `gainXp` does to a character, and the spending of what a level brings (`takePerk`, and `autoAdvance` for the simulator). See the rules below.
- `src/character/worldCasting.ts`: casting out of battle, which is only healing, on the world map: which heals a character can cast now (`worldSpells`) and the cast itself (`castOnWorldMap`), paid from the mana it carries and restoring the average of the spell's dice, so the world map rolls nothing.
- `src/engine/battleEngine.ts`: the battle state machine. Callers only ever:
  - ask `legalActions(unit?)`, `previewMove`, `previewAttack`, `previewCast`, `getState()`
  - call `step(action)`, which returns the `BattleEvent[]` it produced
  
  An `ability` action uses one of the unit's abilities: a routine of strikes at a foe in its attack range, each strike an `AttackEvent` made as `attack` makes one, with the strike's dice plus `abilityDamageBonus` and its `ability`, `strike` and any `status` laid recorded on it; a strike whose target has fallen goes to the nearest standing foe in reach (the lowest id on a tie), and with none it and the rest are not made and log nothing. Or it is an area aimed `at` a hex (legal on the board, a burst within range, a cone or line 1 to range away, touching a standing foe), one `AbilityEvent` resolved over everyone it touches as a hostile area spell is, with the unit's own chance to hit: resistance ignored, its element cut by wards, half the dice (rounded down, no status) on a miss where it has `halfOnMiss` (`CastOutcome.half`); `cast` and it share `strikeUnit` and `aftermath`, so neither may change the other's draws. Each unit's `recharging` (on `UnitRecord` and `UnitSnapshot`, so in snapshots and saves) counts the rounds until a used ability is ready, a round coming off as its side's turn begins, after the ticks and regeneration; `legalActions` lists abilities after casts.
  Events are the engine's only output and are also the log format. **Bump `LOG_SCHEMA_VERSION` whenever an event's shape changes.** Events record more than the player is shown (AP spent and left, the numbers behind each roll, the items behind a gear change); `formatEvent` renders the short on-screen line, so add detail to the event and keep the line simple. An `AttackEvent`'s `melee` says whether the blow was struck with a melee weapon, reach included (`isMelee`), which is how the battle screen tells a swing from a shot. A hit that strikes no image adds the weapon's on-hit effects (`CombatantStats.onHit`, from runes): each entry's flat damage after resistance, cut by the defender's ward of its element and never doubled by a critical (a `bane` entry only against a unit `baneApplies` to), the wielder's heal, and its statuses (an `onCrit` one on a critical only) once the damage leaves the defender standing; none of it draws from the RNG. `damage` stays the weapon's; the rest is recorded in `bonus`, `healed` and `onHitStatuses`, and the defender loses `damage` plus every `bonus[].damage`. `battle_start` records the seed and policies so any battle can be replayed. `snapshot()` gives the whole engine as plain data and `BattleEngine.restore` takes it up again without starting anything over, which is how a battle is saved; it does not change the events, so it needs no bump.
- `src/engine/policies.ts`: AI as pure functions `({ state, legal, rng }) => Action`, registered in `POLICIES`. The game's enemy and the simulator's two sides pick from the same registry. `aggressive` gives each unit the first of: a heal when an ally is at half its hit points or less, Mirror Image or Shield (or Dark Shield) when a foe stands beside it, a hostile area spell that touches two foes or more and no ally (a spell with damage counting only the foes its average damage gets through the ward of; the Web spell one foe or more not yet webbed), Bless on two allies or more, Sleep on the healthiest foe while two stand, Curse on the healthiest foe not yet cursed while two stand, its hardest-hitting spell on the weakest foe (its damage reckoned after the foe's ward), then its best strike, the plain attack or routine of strikes that would do the most harm (each strike the chance to hit times an average hit through the foe's resistance plus its weapon's on-hit damage through the foe's wards, a bane only where it applies, a routine the sum of its strikes', and a routine winning a tie), or in its place an area ability with damage whose net harm (each foe's chance to hit times the mean after its ward, plus half on a miss with `halfOnMiss`, less the same for its own side) is above 0 and above that strike's; then an area ability that only lays a status (Web) where it touches a foe without it and none of its own side; a caster that knows a heal keeps the mana for its cheapest, and none casts Protect or Haste. It judges how close to come by a damaging spell of one foe it has the mana for, else by its weapon. It works over the cast actions `legalActions` lists and what `castTouches` says a cast would touch, so an enemy caster needs only a stat block with `magic`.
- `src/game/encounters.ts`: battle setups, registered by id in `ENCOUNTERS`. A monster location on the world map names the `EncounterId` it leads to and the threat to fight it at, and the simulator fights `goblinRaid` unless told otherwise, so balance runs fight a battle the game has. A setup is built for the party and the threat it is given: the threat decides how many of the encounter's foes take the field and their level (see the rules of scaling below). The party is (a `Fighter` per member: stats and hit points left), lined up on the `PARTY_START` hexes and member i's unit is named `heroId(i)`, which is how `BattleScene` finds the `Character` behind a unit. Each setup also maps unit ids to a `UnitKind`, which is how scenes pick a sprite and how `xpReward` prices the foes (`FOE_XP` times their level); the engine knows only stats. A foe kind (`FoeKind`) is a monster (`MonsterKind`), a stat block scaled from its native level (`FOE_NATIVE_LEVEL`), or a bandit (`BanditKind`) (`src/game/bandits.ts`), built by hero rules: a role's draft made a character, dressed in its role's gear at the grade the threat calls for, levelled and spent by `autoAdvance`, its stats `deriveCombatStats`'s, so a bandit of level L fights as a hero of that draft and gear would; `foeStats(kind, level)` builds either. Each encounter has a band of threats (`ENCOUNTER_BANDS`) and a foe count for each threat in it (`ENCOUNTER_COUNTS`); a threat outside the band is fought as the nearest in it, and `encountersFor(threat)` lists the encounters whose band holds a threat (the blight's spawns draw from `SPAWN_KINDS` alone, so the newer nests do not spawn). `MAX_THREAT` (5) is today's map's highest threat and `threatAt`'s cap, no longer tied to the counts. The Bandit Camp (`bandit_camp`, threats 3 to 7) fields bandits, at two of the map's nests and in the Bandit Gangs the blight spawns from threat 3. The Spider Nest (`spider_nest`, threat 5 only, 3 foes: a Giant Spider, a Kobold Sneak and a Brood Spider) and the Salamander Pool (`salamander_pool`, threat 5 only, 3 foes: a Salamander between two Kobolds) fight with abilities; the Giant Spider (native level 4) webs and bites, the Salamander (native 5) spits fire and is warded against it (`wards.fire` 99).
- `src/game/bandits.ts`: bandits, humanoid foes built by hero rules (`banditStats(role, level, gear)`, cached). Each of the six roles (`BanditRole`: cutthroat, archer, brute, mage, captain, crossbowman; `BANDIT_ROLE` maps the kinds to them) has a fixed, legal `CharacterDraft` and its gear: the Cutthroat an iron dagger, the Archer a yew bow, the Brute a battle axe and breastplate, the Hedge-Mage the Wand of Sparks (Magic Arrow and Shield are its draft's spell picks; `autoAdvance` adds Heal at level 2, Flame Arrow at 3, Heal All at 4 and Fireball at 5, so a mage of level 5 or more, which takes the field from threat 6, casts Fireball and Heal All), the Captain a sword, oak shield and breastplate, the Crossbowman (the Archer's draft) a crossbow. Each is named by catalog family in two ids, tier 1 (iron, oak, yew) and tier 2 (steel, ironwood); the gear is at `banditGear(threat)`, `{ tier, grade }`: tier 1 plain below threat 5, tier 1 Fine at 5 (as before stage 3) and tier 2 Fine from 6 (the user's choice, amending stage 3's Q2: steel at 5 took the threat-5 camp cell from 469 to 256 of 500, and today's map ends at 5), the wand included, as it is a plain item. A hero built the same way (`banditDraft`, the same gear, levels and `autoAdvance`) has the same stats, which a test holds it to.
- `src/game/party.ts`: the `Party`, the player's characters in battle order: the pre-rolled characters a place can be filled with (`PREROLLS`, each a draft and a short role shown under its portrait), the first three of which are the ready-made party (`READY_MADE`, `readyMadeParty`), a soldier, an archer and a mage; the party screen's limit, `STARTING_PARTY_LIMIT` (3), which no party may pass beyond `MAX_PARTY_SIZE` (6, what `PARTY_START` has hexes for); what a won battle brings the party (`rewardVictory`): experience for the living, while the fallen are dead (`buryFallen`, their gear into the baggage); and `autoHeal`, the spending of a party's mana on its wounds as a careful player would from the Spells tab, which camping until healed does.
- `src/game/camp.ts`: camping on the world map: a day of rest (`campDay`) and camping until healed (`campUntilHealed`), the world map's way to restore mana and hit points; each day is a world turn (`passTurn`), and a notable event breaks camp. See the rules of the world map below.
- `src/game/blight.ts`: the blight (`docs/designs/blight.md`): every hex's level, the day's contest of influence over it (`advanceDay`), the blight's growth with time, spawning, and the cleansing a won battle brings (`cleanse`); the `WorldEvent`s a world turn returns. `src/game/territory.ts`: the resources held, and the encampment, captured and lost as their land's level changes, the warnings of a site under threat (`daysToFall`) and the yields to the encampment's stock (`updateTerritory`). The two and `worldMap.ts` import one another, which is safe while none calls another as its module loads. See the rules of the blight below.
- `src/game/buildings.ts`: what the encampment's stock builds, and the stock's arithmetic (`canAfford`, `spend`): the watchtower, built where the party stands (`canBuildTower` gives the reason it cannot, `buildTower` spends and passes the day); the shrine, raised a level at a time at the encampment (`raiseShrine`, no time passing), each level adding `SHRINE_STRENGTH` to the encampment; and the outpost, built by the party standing on a held resource (`buildOutpost`, a day), adding `OUTPOST_STRENGTH` to the site and `OUTPOST_YIELD` to its yield. A tower is `WorldState.towers`, not a location: blight.ts counts it a clean source, vision.ts a watcher and territory.ts loses it as a held site. The shrine is `WorldState.shrine` and outposts `WorldState.outposts` (site ids), read by blight.ts's `siteStrength` and territory.ts's `siteYield`; an outpost falls with its site (`site_lost` with `outpost`).
- `src/game/guildHall.ts`: the guild hall at the encampment (`atGuildHall`): its level (`WorldState.guildHall`), which sets the party limit (`partyLimit`, derived, never stored: 3, 4, 5), its upgrade for the stock, recruiting into the reserves (from a pre-roll or a created draft, at `recruitLevel`: the hall's level or the party's lowest, whichever is less, with the levels' points unspent), and moving heroes between the party and the reserves. Each action returns why it was refused, or null.
- `src/game/tradingPost.ts`: the trading post at the encampment (`WorldState.tradingPost`, built from the start at 1): its levels (1 to 3 sell tier 1 at grades up to the level, 4 adds tier 2 at every grade, `sells`); `wares(world, filter)` lists what it sells, narrowed by slot or family; buying plain items at a grade into the baggage, priced by family (`PRICES`) times the tier's and the grade's multipliers (`TIER_PRICE`, `GRADE_PRICE`), selling from the baggage and backpacks (never what is worn) for half, a modifier adding nothing, an enchanted item half its `VALUES` and an embedded rune half its price on top (`salePrice`; the post never sells a runed item); rune wares (`runeWares`: Ember, Rime, Storm, Stone, Wind and Life at rank 1 from level 2 and rank 2 from level 4, `RUNE_PRICES` 15, 45, 135, 405 by rank), `buyRune` into the pouch (`GameState.runes`) and `sellRune` from it for a third, and selling materials two for a gold piece; it never sells materials. `src/game/crafting.ts`: crafting, putting a modifier at a grade on an item where it lies (`craft`), replacing any it had: in the field (`craftTier` is `'field'` anywhere the party may camp, the encampment without a workshop included), the field modifiers at grade 1 and a day (`passTurn`); at the workshop (`WorldState.workshop`), the modifiers its level unlocks up to the grade of its level, no time passing. `src/game/runecraft.ts`: runecraft, runes moved between the pouch (`GameState.runes`) and an item's sockets where it lies: `embed` fills the next empty socket, at the workshop of any level for any rank, or a rank-1 rune in the field (where the party may camp) for a day (`passTurn`); `fuse` makes three of a rune one of the next rank, to rank 2 from workshop level 1 (ranks 3 and 4 ask levels 4 and 5, which stage 10 adds, so they are refused for now, the refusal naming the level, checked before the count); `extract` takes a rune back intact from workshop level 2, the rest closing up; embedding costs 5 gold a rank, fusing 10 a rank of the new rune and extracting 10 a rank; no time passes at the workshop; a change to a worn item keeps its wearer's share of hit points (`replaceAt` ends with `clampHp`). `src/game/infirmary.ts`: the infirmary (`WorldState.infirmary`) and `restHealing`, what a day's camping heals a member where the party stands, which `campDay` uses. `src/game/itemPlace.ts`: `ItemPlace`, where an item the trading post or crafting acts on lies (baggage, worn, backpack) with the id expected there, so a place that no longer holds it is refused as stale; a worn item replaced or removed through it ends with `clampHp` on the wearer, as a Life rune may move the maximum. Each action returns why it was refused, or null, and checks everything before changing anything.
- `src/game/loot.ts`: rune loot after a win (`takeRunes` into the pouch), drawn from a stream of its own seeded from the battle's seed (`lootRng`), so the battle's dice are untouched: by threat, a nest's leader favouring its element (`FAVOURED_RUNES`); the rows past threat 7 and the Source's own wait for stage 9 (the Source rolls threat 5's). `BattleScene.endBattle` calls `takeRunes` for a win at a monster location, and the simulator after each win; a debug `fight` rolls none.
- `src/game/encampment.ts`: what the encampment screen shows: every facility (`FACILITIES`: the guild hall, the shrine, the trading post, the workshop, the infirmary), built or not, its level, what it does and what its next level costs, and `improveFacility`, which calls the facility's own module. A new facility needs an entry there, a sprite and a plot (`encampmentView.ts`), and a scene in `EncampmentScene`'s `OPENS` if it has a screen of its own.
- `src/game/vision.ts`: fog of war, what the player knows of the world map: the hexes in sight (`visibleHexes`), and `updateSight`, which every change to the land ends with, remembering what is in sight and telling of monsters newly sighted. Knowledge only: the rules run on the true state and the simulator ignores it.
- `src/game/ground.ts`: `Ground`, the loose items lying on a battlefield, one pile per hex, and `pileChanges`, which tells what a visit to the inventory dropped and picked up. `BattleScene` holds one `Ground` per battle; the engine does not track it; `fromPiles` puts a saved battle's back.
- `src/game/worldMap.ts`: the world map's state and rules, Phaser-free like the battle's: `WorldState` (the board, the party's hex, the turn count, the locations, each monster location with its fixed `loot`, the blight's levels and counters, what the player has seen of them (`seen`, `sighted`), the held sites, the stock, the world RNG's state and the game's `status`) and the functions that change it (`passTurn`, through which every turn passes; `travel`, `linger`, `clearLocation`). They take the party, whose levels are its influence. `WorldScene` asks `routeTo` what a click would do and must not decide it. See the rules below.

It is created by the party screen, or read from a slot, and passed through scene data, never held in a module global. A game with no slot (`newGame()`'s default) is never saved: the simulator's, a test's.

Text may say `{encampment}` and `{leader}` (`fillText`). A new moment needs a case in `StoryMoment` and a scene that raises it; a new anchor a name in `TutorialAnchor` and a place in the `anchors()` of the scene that has the control.
- `src/game/save.ts` and `src/game/saveSlots.ts`: the save format (a `SaveFile` to a string and back, storage-free) and the three slots in `localStorage` that hold the strings, reached through `src/storage.ts`, the guarded `localStorage` the audio settings share. See the rules of saving below.

Rules of the battle system worth knowing before touching the engine: a side's units act in any order and the turn ends manually; units get 8 AP a turn by default, a move costs 1 AP per hex (`MOVE_AP_COST_PER_HEX`) and an attack costs the unit's `attackApCost` and reaches foes within its `attackRange`, both of which come from its weapon (`ItemStats`; the longsword costs 5 and reaches 1 hex, the bow costs 4 and reaches 5, so that a unit of 8 AP standing still shoots twice, and the light blades cost 4 and the dagger 3, for two blows; see the note over the weapons in `catalog.ts`); a melee weapon is one of range 1 or with `reach` (`isMelee`, which the engine asks wherever it tells a blow from a shot): the spear and the halberd strike from two hexes as melee weapons, with Melee Weapons, strength's damage, the melee perks and piercing, a range of 2 being an ordinary attack range; nothing blocks a shot or a spell, as there is no line of sight yet; a two-handed weapon and an off-hand item cannot be held together, so equipping either stows the other (`equipFromBackpack`), or drops it on the ground when the backpack has no room, and the inventory shows the weapon ghosted in the off-hand slot; stepping from a hex adjacent to a ready foe with a melee weapon, reach included, to one that is not provokes one free attack (a reach weapon's zone is still its neighbouring hexes only; a step to another hex beside it provokes nothing; one per unit per enemy turn, decided in `reactorsAt`, which `reachableHexes` asks about each step; ranged weapons, wands and the crossbow among them, hold no zone of control); bonuses to the chance to hit, in percent, stack from flanking (`FLANK_BONUS_PER_ALLY`) and from the arc struck (`ARC_BONUS`, judged at range by the neighbouring hex the shot comes in over); defence has two axes: armour class (agility, shields, the breastplate a little, statuses) comes off the chance to hit, and `resistance` (what armour stops, and a monster's own hide or plates) comes off the damage of every weapon hit, as flat points, a hit that rolled anything doing at least 1 (`damageThrough`); a flat cut and not a share, so that it tells most against weapons that hit often and lightly, the dagger, the shortsword and the bow, which are the weapons for the lightly armoured; a melee weapon and the strength perks pierce points of resistance (`armorPierce`, `effectiveResistance`), most of all the heavy weapons, which are the answer to the armoured; nothing pierces armour class; a shot, a wand's included, pierces nothing but the crossbow's own piercing (`rangedPierce`; the strength perks' piercing is a blow's, never a shot's), and a spell's damage, a status's ticks included, owes nothing to resistance, nor does an area ability's, nor a weapon's on-hit damage (runes), which is warded instead; an on-hit `bane` (the Dawn rune) applies only against a unit with `regeneration` or `blightborn` (the Blight Horror), and Seared laid on a hit (an Ember rune of rank 3) stops regeneration as Fireball's does; `previewAttack` gives the resistance left after piercing, which the battle screen shows on the foe's nameplate as "−N dmg"; a unit with `regeneration` regains that many hit points as its side's turn begins, after its statuses' damage (a `regenerate` event), unless a status with `stopsRegeneration` is on it (Corroded, from Acid Arrow, which also takes 2 off resistance, and Seared, laid for a turn by Fireball and Flame Arrow); facing is automatic, set by moving, attacking and casting, and once each enemy turn a unit struck in its side or rear by a melee weapon, reach included, hit or miss, turns to face the attacker before the roll (a shot, a wand's included, or a spell gives no turn and spends none) (`turnReady`, readied with `reactionReady` and never for the side taking its turn, so a mover struck by a free attack cannot turn; `AttackEvent.defenderTurned`); a second attacker from another side then finds the arc that exposes, and previews, the AI and `planAttack` judge the arc by `arcStruck`, the front for a melee blow (`isMelee`) on a foe that can still turn.

Rules of casting (`docs/designs/spells.md`): a unit whose stats have `magic` may cast a spell it knows, for the spell's action points and mana, at what the spell is aimed at (`Spell.target`): a standing foe within range, a standing ally within range (itself included), itself, or an area, a hex of the board within range (its own for a spell of range 0, Bless and the Heal Alls) whose radius touches every standing unit around it. The cast action names a `target` unit or, for an area, the hex `at` its centre. A hostile spell (offence, and Bane) rolls to hit each unit it touches, in roster order, as an attack does (`rollToHit`, then the dice on a hit, so the RNG is drawn from the same way), with the caster's spell skill for its chance and its own critical chance; flanking and facing add nothing to it: the spell is the reliable strike, the blade the one that rewards position. A hostile area touches everyone in it, the caster's side and the caster included, and is illegal where it holds no foe; a cast that fells the last of both sides loses the battle, as the player's side is judged first. A friendly spell never misses, touches only its own side and heals up to the maximum. A spell's area has a shape (`Spell.shape`, a burst when left out; a cone or line is aimed 1 to `range` hexes from the caster and reaches `range`), worked out by `areaOf`, which the scene also draws from. `castTouches` (over `areaTouches`) says whom a cast would touch, for the engine, the policies and the battle screen alike, and `previewCast` the odds on each. A spell or a status's tick may have an element (`Spell.element`, `StatusRule.element`: Flame Arrow and Fireball fire, Frost Blast frost, Acid Arrow and Corroded acid, Death Cloud and Poisoned poison, Lightning Bolt lightning), and a unit's ward against it takes its points off each hit (after a critical's doubling) and each tick (`warded`, recorded on the outcome and the tick as the points stopped, and logged as "(warded N)"); a status is laid whatever the ward stopped, and a tick warded to 0 wakes no sleeper. A spell with `drain` (Drain Life) heals its caster that share of the hit points its targets lost (none for damage past what a target had left), rounded down and no more than it had lost (`CastEvent.drained`). Lasting effects (`STATUSES`: asleep, chilled, corroded, poisoned, shielded, protected, blessed, baned, hasted, mirrored, seared, cursed, webbed) are `UnitRecord.statuses`, and `effectiveStats` adds what they do to armour class, resistance and the chance to hit, which every roll reads. A status lasts its unit's own turns, counting the one under way if it is laid on its side's turn, and ends after the end of the last (`status_end`); laid again it takes the longer duration, and different ones stack. AP changes apply as the unit's turn begins, and at once on its own turn; damage over time is dealt as its side's turn begins, unit by unit in roster order (`status_tick`), and may end the battle there, so `startTurn` returns events. A sleeper gets no AP, holds no zone of control and is struck with `HELPLESS_BONUS`, and any damage wakes it; a hit on a mirrored unit strikes an image and draws no damage dice. A unit that falls loses its statuses, and none outlasts the battle. A cast turns the caster to its aim, ends a paid-for change of gear as an attack does, and provokes nothing. `legalActions` lists casts after a unit's attacks, also for a unit with too few AP to attack, spell by spell, units in roster order or an area's centres in board order. Mana is a battle's budget: `UnitRecord.mana` starts at `magic.maxMana` whatever the character carried in and never comes back in battle; what a winner has left is copied back to its character, to heal with on the world map until the next battle, a level or a day of camping fills it.

Gear can be changed mid-battle. The inventory opens for the selected unit (I or C) and edits its `Character` directly (`equipFromBackpack`, `unequipToBackpack`), and when it closes `BattleScene` sends the engine an `equip` action carrying the newly derived stats, one for each member whose gear was changed while the panel was open (its portraits turn it from member to member), since the engine knows stats and not items; the action also lists the items changed (`gearChanges`), which the engine only copies into the `equip` event. New stats never add mana to spend: the engine keeps what is left, within the new maximum. Items can be dropped on that unit's hex and picked up from it the same way: the inventory's Ground section edits that hex's pile (`dropFromBackpack`, `dropEquipped`, `pickUp`; right-click or Ctrl+click drops, a click on a ground item picks it up into the backpack, and a pile deeper than the grid scrolls with the wheel)., and the same `equip` action lists what was `dropped` and `pickedUp`, again only for the log. An item can also be dragged between the backpack, the equipment slots and the ground, a drop making one of those same changes or nothing (`gearDrag.ts`; dropped on its slot it is equipped there, so a ring goes on whichever ring slot it is dropped on, the optional slot of `equipFromBackpack`); a primary click therefore acts on release, and a press that moves more than `DRAG_THRESHOLD_PX` is a drag. Equipping, stowing, dropping and picking up share one cost: a change costs `EQUIP_AP_COST` (1 AP), paid once: further changes are free until the unit moves or attacks or its turn ends (`equipCost`). `legalActions` never lists `equip`, so the AI policies do not change gear.

On the world map the same panel changes gear at no cost, with the party's baggage where the ground is (`WorldScene` passes `gearApCost: 0` and `ground: gameState.baggage`): a click takes an item from the baggage into the open member's backpack, a right- or Ctrl+click puts one in, and so an item passes from member to member. Nothing is told to anyone when the panel closes, as the characters and the baggage were edited in place. Only a Life rune's `maxHp` changes maximum hit points (in armour or a shield; in a weapon Life heals on a hit) (`maxHp` adds the worn items'), so every change to what a character wears ends with `clampHp(character, maxBefore)`, the maximum read before the change: when it moves the hero keeps the same share of its hit points (the user's choice, both ways), `min(max, max(1, round(hp × max / maxBefore)))` (never above the new maximum, never to 0 from a positive value, so taking Life gear off and putting it back leaves `hp` where it was, within rounding, and a full hero stays full), and a hero at 0 stays at 0. That share rule is outside battle; in battle the rule is the engine's, whose `equip` only lowers hit points to the new maximum, so Life armour put on mid-fight heals nothing, and the character panel changes gear there by the cap rule (`HpRule` 'cap', which `BattleScene` hands the panel as each member's `hpRule`), so it shows what the engine holds. `equipFromBackpack`, `unequipToBackpack` and `dropEquipped` do it, by the rule they are given; a new way of changing what a character wears must too. In battle the engine's `equip` clamps `hp` to the new maximum. A ring (`Item.ring`) fits either ring slot: clicked, the first if it is empty, else the second, else in place of the first; dragged, the one it is dropped on.

Rules of the encampment's gear (`docs/designs/expeditions-and-encampment.md`): a plain item's grade comes from the trading post and its modifier from crafting; a grade adds damage (and at Masterwork, to hit) to a weapon, armour class to a shield or a small-slot item and resistance to body armour, and a modifier trades one stat for another (Bearded a point of piercing a grade, Reinforced a point of resistance), Light alone moving a weapon's AP (the longsword and axe to 4 and 5); nothing moves the bow off 4 AP. Gold is the contested resource: the guild hall, recruits, the shrine, gear and crafts all want it, and the far materials (stone, copper, silver, crystal, peat, salt) buy the higher levels of the trading post, workshop and infirmary and the higher grades of craft. A damage bonus a modifier lowers may go below 0, so a hit's damage is kept at 0 or more (`rollHitDamage`).

Rules of the world map: the encampment is the only settlement (`kind: 'encampment'`, `ENCAMPMENT_ID`), named by the player when the game begins (its location's `name`, read through `encampmentName`, never assumed to be Oakvale), and every other quiet location is a resource; the map (`WORLD_SIZE`) is several windows across, and `WorldScene` scrolls it to follow the party, or where a drag on it pans it (a press that moves no more than `DRAG_THRESHOLD_PX` is a click to travel), until the next journey, Home or a click on the party's entry in the list down its right brings it back to the selected party (`centreOnSelected`); time passes in turns, one per hex travelled, and every turn is the blight's day (`passTurn`); fog of war hides the rest (`vision.ts`, `docs/designs/guild-hall-and-watchtowers.md`): the party, the encampment, each held site and each watchtower see every hex within a radius (`PARTY_VISION` 5, `CAMP_VISION` 6, a resource 2, a tower 8; nothing blocks sight), a hex once seen is remembered at the level it last had in sight (`WorldState.seen`, -1 never seen) and a monster location once seen stays known (`sighted`); the Source is unknown at the start too, a mystery found only by exploring, and its sighting (`source` on the `sighted` event) is notable however far off; a journey is walked a hex and a turn at a time and stops where a notable event happens (`isNotable`: monsters sighted within `NOTICE_RADIUS` of the party, the Source wherever it is sighted, a held site or tower newly under threat or lost, the encampment lost; a spawn is told only when sighted) or where monsters stand on the road; routes keep clear of every sighted monster location except one they end on, and go through the unexplored as through open land; walking into monsters sets `confronting`, and the party cannot travel on until it scouts, waits (a turn each, and neither does more yet) or attacks; on a held resource the party may build an outpost (`buildOutpost`, a day, `OUTPOST_COST`); anywhere but among monsters the party may build a watchtower on clean land off every location, `TOWER_SPACING` (4) hexes from any other, for `TOWER_COST` from the stock wherever the party is, in a day (`buildTower`), and may camp (`camp.ts`), a turn a day, each day healing every member `NATURAL_HEALING_PER_DAY` (1), or more with the infirmary (`restHealing`: a third, then all of it at the encampment, then 3 a day elsewhere), and filling every caster's mana, and camping until healed casts the party's heals with the mana it has (`autoHeal`), then camps a day and casts again while anyone is wounded, unless a notable event breaks camp; a won battle takes its location off the map, cleanses the land around it and puts its loot in the baggage (`BattleScene.endBattle` calls `takeLoot` and `clearLocation`, and the victory screen names what was found). Nothing is done in time but the turn: the game ends only when the encampment falls (`status` 'lost', permadeath as a defeat in battle is) or the Source is beaten ('won'), after which the player ends the game, keeping the save, or goes on in 'endless' mode.

Rules of the blight (`docs/designs/blight.md`): every hex has a level, 0 (clean) to 3 (corrupted), kept densely in `WorldState.blight` by `boardIndex`. Each day each hex's `shift` counter moves by its net influence, blight less clean, and its level by one when the counter reaches `SHIFT_COST` either way. Each source pushes with its strength less a point a hex of distance: a monster location with `BLIGHT_PER_THREAT` × its threat, the Source with `SOURCE_STRENGTH`, each corrupted neighbour with `CREEP`, all times the blight's growth with time (`blightGrowth`: a tenth more every 30 days, to half again at day 151, worked out from the turn); against them the encampment (`CAMP_STRENGTH`, more with its shrine), each held resource (more with an outpost), each watchtower (`TOWER_STRENGTH`), and the party, with `PARTY_BASE` and half its levels together (nothing else of the party counts). A monster location's hex stays blighted or worse until it is beaten; the party's hex is neutral, so the blight never rises there nor creeps from it, but the party's influence lowers it. The fixed sources' influence is worked out again only when a location or a held site changes (`fields`, a memo outside the state). Corrupted land builds spawn pressure, and each `SPAWN_COST` of it puts a monster location on corrupted land clear of the party, the nests and the held sites, drawn with the world RNG (whose state is saved), at the threat of where it lies (`threatAt`, never the blight or the date, so the home band's nests stay ones a weak party can beat), its kind drawn among those whose encounter band holds that threat (a Goblin Brood, a Kobold Nest, and from threat 3 a Bandit Gang), up to `MAX_MONSTER_LOCATIONS`. A won battle lowers the land within 1 + its threat by two levels. A resource is held while its land is clean enough: captured at level 0, lost at `LOSS_LEVEL` (2), under threat (with the days until it falls) while the blight is gaining on it; every `YIELD_DAYS` each held site adds its yield to the encampment's `stock`, half if tainted, which the buildings (buildings.ts) and the guild hall spend. A watchtower is lost, and warned of, as a held site is. Spawns keep `SPAWN_CLEARANCE` from towers too. The Source (`SOURCE_ID`, far in the east) fights its own encounter at threat 5 (`source_guardians`): the Blight Horror, a boss whose claws pierce 2 points of resistance and which casts Death Cloud and Bane, with a Goblin Brute, a shaman and a Kobold Sneak. The constants were tuned with the campaign simulator, not by design.

Rules of saving: there are three slots (`yomi.save.1` to `3` in `localStorage`) and a playthrough lives in one from Begin to its end, written by the game itself (`saveGame`); there is no save button and only one save of a playthrough. `WorldScene` saves as it opens and after everything that changes the game (a journey, as it is begun; scouting, waiting or camping; the closing of the character panel). `BattleScene` saves each time the player's turn begins, the first included, with the battle: the engine's snapshot, where the enemy's RNG stands and the ground's piles; a reload therefore rewinds to the start of the turn, with the same dice. A victory is saved as it happens, before the victory screen is left; a defeat deletes the slot (permadeath) and clears the game's `slot` so that nothing writes it back, and so does the encampment's fall, on the world map. A loaded battle builds its encounter again from the location, for the units' kinds and the experience it is worth, and takes everything else from the save. In the saved string every `Item` is its id, put back by `itemById` as the constant or the graded or modified item it builds and remembers, so identity comparisons hold after a load and an item's tuning reaches old saves; a new base or enchanted item must be in `BASE_ITEMS` or `MAGIC_ITEMS` or a game holding it cannot be loaded. There is no migration: raise `SAVE_VERSION` whenever the shape of `GameState`, `Character`, `WorldState` or `BattleSnapshot` changes, and older saves read as unreadable, which the menu lists and will not load. Saves need not stay compatible while the game is in development: break the format whenever a change calls for it, and raise the version rather than work around old saves. A browser that refuses storage still plays; the scene says once that the game could not be saved.

Rules of scaling: monsters are the more dangerous the further from the party's home they lie. A monster location's `threat` is 1 within `THREAT_BAND` (11) hexes of the encampment and one more for each band beyond, up to `MAX_THREAT` (5) (`threatAt`), and `WorldScene` tells the player the threat of the monsters it stands before. Each encounter has a band of threats (`ENCOUNTER_BANDS`, `encountersFor`; the monsters' five are 1 to 5, the Bandit Camp 3 to 7) and a foe count for each threat in it (the monsters' five all 2, 3, 3, 3, 4; the Bandit Camp 2, 2, 2 at threats 3 to 5, and 4, 4 at 6 and 7, a first guess for the stage that grows the map), and a threat outside the band is fought as the nearest in it. A battle at threat T fields that many foes, all of level T, the first of the encounter's slots that take the field at T (`FoeSlot.fromThreat`). A monster kind has a native level (`FOE_NATIVE_LEVEL`, 1 but for the Giant Spider's 4 and the Salamander's 5; `foeStats(kind, level)` builds a foe), its stat block written for that level, and a level above it adds to the monster 70% of its level 1 hit points (`FOE_HP_PER_LEVEL`), 5 to its chance to hit and to its armour class, 1 damage every second level, and to a caster 3 mana and 5 to its spells' chance (`foeAtLevel`, from the native level); `foeYardstick(level)` gives the ranges a foe of a level should sit in, which a test holds each kind to at its native level; its resistance and regeneration are its kind's at every level. Goblin Raid's third foe is the Goblin Shaman, so it fights from threat 2, and its fourth the Kobold Sneak. The armoured foes are the Hobgoblin Chief (resistance 4, the Hobgoblin Warband, at threat 2 on the map) and the Armoured Troll (resistance 5, regeneration 2, one heavy blow a turn), which the Troll Lair fields only at threat 5, beside a Troll (resistance 1, regeneration 3, two claws a turn: both as one 8 AP routine, `troll_claws`, standing still, or one 4 AP claw after a move); at threat 4 the ready-made party won 7 Troll Lairs in 500 with the Armoured Troll in it, its bow and wand doing about 1 a hit, as the simulator's heroes never change weapons. Rules of characters, which follow Fallout 1 and 2: a character has six attributes from 1 to 10 (`ATTRIBUTE_IDS`), adding up to `ATTRIBUTE_POINTS` (32) at birth, which is one short of three at 10: one at 10 leaves two at 7 and the rest low, two at 10 leave the others near 3; perks raise them from there, and the sum is the attribute everywhere (`attributeLevel`). They give it hit points (10 + strength + endurance, and 2 + half its endurance a level), action points (5 + half its agility), armour class (agility, plus armour, shield and enchanted gear; its resistance is only what its armour stops), its critical chance (luck) and a little melee damage (strength), and they set where each skill starts. There are three skills, each a percentage (`SKILLS`): Melee Weapons, Archery and Magic. They start low, from attributes alone (strength + agility, perception + agility, twice intelligence), so that the rest is the character's choices: one skill is tagged, which adds `TAG_BONUS` (20) and doubles what a skill point buys, and a raise costs 2 points from 80% and 3 from 90% (`SKILL_COST_TIERS`). `skillLevel` is the skill everywhere, perks' share included. An untagged, untrained skill sits near 10%, which the engine's floor makes a 5% chance against anything armoured. A weapon skill is the chance to hit with that kind of weapon before the foe's armour (`weaponSkill`: Melee Weapons, bare hands included, which roll a fixed 1d4; Archery for a weapon that reaches further than a hex and has no reach; or the skill the weapon names, which for a wand and a staff is Magic). Gear has weight (`deriveCombatStats`): each worn item that asks more strength (`ItemStats.strength`, read against `attributeLevel`, so a trunk perk helps) than the wearer has costs `SHORTFALL_TO_HIT` (5) to hit a point short, item by item and added up (`strengthShortfall`; an off-hand item under a two-handed weapon counts for nothing), against weapon attacks only; an item's `apPenalty` comes off action points every turn (plate and the tower shield 1 each); heavy gear's negative `spellSkill` lowers spells (plate −15, the breastplate, helm and gauntlets −5), which is how weight tells against a caster. Runes give a hero wards (`CombatantStats.wards`, summed over everything worn), which take their points off each hit and tick of their element as a monster's do. The iron breastplate every hero starts in asks strength 3 (the user's decision, after 4 cost the strength-3 ready-made archer and mage 5 to hit and the guard 56 campaigns), so those two lose nothing to it, and a wearer of strength 2 loses 5. A wand is in every other respect a ranged weapon: no mana, no zone of control, nothing from strength, and the archer's perks apply. Magic is also the chance of a spell striking, and what spell perks ask for. There are no classes.

Rules of creation (`creation.ts`): all six attributes start at 1 and the player places 26 points (`CREATION_ATTRIBUTE_POINTS`, so they add up to `ATTRIBUTE_POINTS` as ever), all of them, none above 10; tags one skill and places 10 skill points (`CREATION_SKILL_POINTS`); spends 3 perk picks (`CREATION_PERK_PICKS`) in the perk tree; and gives a name (at most 12 letters, unique in the party, as the battle log tells units apart by name) and one of the preset portraits. Creation has no rules of its own about what a point or a perk does: `draftCharacter` spends them with `raiseSkill` and `takePerk`, so nothing a perk asks is waived, and a perk must be open to a level 1 character. Skill points and picks left unspent stay on the character, to spend on the world map as those of a level are. A change that leaves a chosen perk unqualified drops it and returns its pick (`pruneDraft`), and the screen says which. Starting gear is not chosen: a character holds the weapon of its tagged skill (`STARTING_KIT`), wears an iron breastplate (whose spell skill −5 a caster pays) and carries every other plain weapon. A specialist (its skill tagged, all 10 points in it, a rank of its skill perk) starts near 60% when its skill's attributes come to about 15 (strength 9 and agility 6, say), which is the trade-off: a 60% start leaves less for the rest. The prerolls, the ready-made three among them, are drafts like any other, held to the same rules by a test. The party being built is a list of drafts, which is what lets a character be edited until the game begins; the drafts are not kept after that.

Rules of perks and spells: a perk (`PERKS`) is data: what it asks (level, attributes, skills, and a rank of the perk it `requires`), how many ranks it has, what a rank adds (`PerkEffects`, which `perkBonus` sums wherever that number is derived) and the `spell` it teaches, if any. A new perk whose effect is already a key needs only an entry, and a new kind of effect needs a key and a reader. The perks form a tree with a `branch` for each attribute, and the spells a tree of their own (below). Most perks ask level 1, so a new character's three picks have something to buy; each skill has a perk that adds 5% to it a rank, for two ranks (Weapon Training, Marksmanship, Arcane Study: a `PerkEffects` key for each skill id, read by `skillLevel`, so it counts towards what another perk asks). A branch's trunk is the perk that raises its attribute by 1 a rank (`TRUNK_PERKS`, two ranks each from level 3, never past 10, and so not for a starting character, whose attribute points creation has already counted); the other perks grow from it, and one further out names the one before it in `requires`. Each branch ends in perks of level 6 that ask 8 of its attribute (Weapon Mastery and Eagle Eye, +10% to their skill, Mighty Blow, Sunder, Tireless, Deep Well, Arcane Mastery, Evasion, Fortune): with picks at levels 3 and 6, a character born at 7 reaches them by its trunk, which is what makes attribute points worth something after creation. The strength branch has a third line besides blows and skill: Armour Breaker and Sunder, which make melee blows pierce armour. The perk tree has room for 3 columns and 11 rows (`PerkTreeView`, whose strip sits under however many rows the layout has; 11 fill the panel), and every place a perk could hang is taken, so a new perk needs the view reworked. The trunk is not asked for by the perks of its branch: it is how a character short of an attribute gets there, since a raised attribute counts towards what perks ask. A raise changes at once everything the attribute feeds, hit points of past levels included (they are derived), but not skill points already handed out (they are banked). A character knows exactly the spells its perks teach (`knownSpells`); one that knows a spell has mana (`maxMana`: twice its intelligence, half its intelligence more a level, and what its gear and perks add), and one that knows none has none, whatever it wears. An item's `spellSkill` helps spells strike but counts neither towards what a perk asks nor for a wand. Spells are learned through Spellcasting, a perk of the intelligence branch (level 1, Magic 40%), which teaches none itself: it brings two spell picks (`SPELLCASTING_SPELL_PICKS`) and a spell pick with every level after. Each spell is a spell perk (`school` set, keyed by its spell's id, built by `spellPerk` and listed after the attribute perks), drawn in the spell tree and not the perk tree: three schools, offence, healing and support, each grown from the spells that ask only Spellcasting, a spell further out asking the one before it and its tier's level and Magic (`SPELL_TIERS`: level 1 and 40%, 3 and 55%, 5 and 70%). `takePerk` pays for a spell with a spell pick if there is one, else a perk pick, and for anything else with a perk pick; a perk that raises the maximum mana raises what is carried by as much, as one that raises hit points does. The spell tree uses 3 columns and 9 of the view's 11 rows.

Rules of progression: winning a battle earns the experience its foes are worth together (`xpReward`), a foe of level L being worth L times what its kind is worth at level 1, awarded by `BattleScene` when the battle ends (`rewardVictory`); the engine and the simulator know nothing of it. Every living party member earns the whole reward, so the yardstick below holds for each hero whatever the party's size. A member who fell in a won battle is dead (permadeath): out of the party for good, what they wore and carried put in the baggage, and named on the victory screen; the party fights on smaller until the guild hall fills the place. A battle is lost only when every member has fallen, and that ends the game, reserves or not. Reserves earn nothing. Wounds are carried from battle to battle; a new level heals fully, and otherwise hit points come back by healing spells, in battle or on the world map, and by camping, a hit point a day; mana spent on the world map is refilled by a day of camping, but not by waiting or travel. A foe's worth is fixed by its kind and level, while each level costs more than the last, so early levels come fast and later ones slowly. The yardstick is the even foe, worth `EVEN_FOE_XP_PER_LEVEL` × the hero's level, with a weak foe at half that: level 2 costs a little under one even foe, and after that leaving level L costs L − 1 of them. Price a new monster against that yardstick. A level brings hit points, skill points (2 + a third of the hero's intelligence, so 2 to 5, kept few because a tagged skill doubles them) and, every `PERK_LEVEL_STEP`th level, a perk to pick (besides the three of creation), and to a hero with Spellcasting a spell pick; it heals the hero fully and fills its mana. The points and the pick wait on the character until the player spends them, which is done on the world map and not in battle: stats changed mid-battle would have to reach the engine as an `equip` action does. A perk is chosen from the perk tree and a spell from the spell tree, and nowhere else.

When the game is won or lost a screen covers the map: End (to `Menu`, the save kept) and Continue (endless) after a victory, Main Menu after the encampment falls. Attacking a monster location starts `Battle` with that location's id; a victory clears the location and returns to `World`, and a defeat deletes the game's slot and goes back to `Menu`. `Inventory` is the character panel (its item tooltip lists an item's sockets and runes below its stats, and its stat lines, on the Character and Inventory tabs, carry a `Wards:` line while any ward is above 0, and the Character tab an `On a hit:` line for the main hand's runes (`onHitLines`), which the Inventory tab, short of room, leaves to the weapon's tooltip), an overlay showing one party member at a time in four tabs (Character, Skills, Spells, Inventory): over `Battle` (C, S, B, I), where gear can be changed for an action point but skill points, perks and spells are only shown, and over `World` (C), where all can be spent and gear is changed freely, through the baggage. The Skills tab lists only the perks a character has taken, spells aside; its Perk Tree button (or P) swaps the panel's content for the perk tree, a view with no tab button of its own, where a click on an open perk takes it and Esc steps back to the Skills tab. The Spells tab lists the spells known, the mana carried and the spell skill, gear included, and its Spell Tree button (or K) opens the spell tree the same way; on the world map a heal's Cast button casts it (`castOnWorldMap`), a heal of one asking for a portrait to be clicked (`worldCast`). It is handed the whole party (`PanelMember`s: each character, and in battle what its gear may do) and the member to open on, and when it closes it tells the scene under it which member it last showed, as the data of the resume.

The party's portraits run down the left of `World`, `Battle` and `Inventory` alike (`PartyColumn`, placed by `partyPanel.ts`), so they seem to stay put under the panel. One member is the active one, marked in gold: in battle the selected unit, on the world map only the member a panel opens for. A click on a portrait makes its member active and a click on the active member's opens its panel (`portraitClick`); in battle a member that cannot be selected (spent, fallen, or during the enemy's turn) has its panel opened at once. A click on a portrait beside the open panel turns the panel to that member. `Menu` is an overlay over `World` or `Battle` (Esc). Both are told which scene to resume by their `resume` scene data; overlays pause the scene under them and resume it on close.

`BattleScene` is a view over the engine: it turns clicks into `Action`s, calls `engine.step`, and plays back the returned events. It must not decide outcomes. Every battle is seeded, by the page's address or else at random, the enemy's RNG with the seed plus one, so that any battle can be saved and replayed from its log. A click on a foe always means a weapon attack, from where the unit stands if it can, else after the walk into reach that leaves the AP for it (`planAttack`), and nothing at all when no such walk exists, as a walk that cannot end in the attack is a plain move, a click on a hex (hovering that foe says why in the header hint, in the warning colour, `noStrikeHint`: "Too few AP to reach and strike", or "Too few AP to strike" for a foe in range; the hint wraps at the window's width and the usual one is kept to one line at 840 wide, as the party's column covers a second); a spell is cast with the Cast button (M), shown for a unit with magic, which opens a list of its spells (`spellMenu.ts`), each greyed when it cannot be cast now and picked by a click or its number; the spell then asks for its target even when there is only one (`targeting` holds what the next board click picks a target for), and hovering an area's centre outlines the area and shows the odds on every unit it would touch, allies included. The pointer over a valid target is the crossed swords for a weapon attack or hostile spell, or a green cross for a friendly one (`spellCursor`, `CURSORS.heal` in `cursors.ts`). Nameplates show each unit's statuses as coloured letters beside the hit point bar. Hovering a standing foe that has abilities or wards shows a small panel beside it (`foeInfoLines`; the probe's `foeInfo`), its name the title and each ability's description dimmer under it, drawn at its own size however far the board is scaled down, cleared as each event plays and drawn again when playback ends. A hit's on-hit damage floats over the defender as "+3 fire" at its own size (`bonusText`, in a layer of its own), and a Life rune's healing refreshes the attacker's hit points; the nameplates' status letters are redrawn for a status a rune laid as for one an attack did (`changesStatusMarks`). A win at a monster location rolls its runes into the pouch when the battle ends (`takeRunes`, seeded from the `battle_start` seed in the log, so a reloaded battle finds the same; a battle with no location rolls none) and names them with the items on the "Found:" line. A routine's strikes play as successive attacks, and an area ability (`AbilityEvent`) plays through the spell-effect path: its hexes flash and each unit touched shows how it fared. Scenes use Phaser's `RESIZE` scale mode, so each one positions everything in a `layout()` method that reruns on resize; the game is held at a minimum of 840×560 (`MIN_GAME_SIZE` in `src/main.ts`), below which the page scrolls. `World` and `Battle` lay their map, board, log and buttons out to the right of the party's column (`PARTY_PANEL_W`).

Scene logic that can be expressed without Phaser is pulled into sibling helper modules, and new logic should follow suit: `eventSchedule.ts` (timing of event playback), `battleEffects.ts` (how a blow, a shot, each spell and each area ability look and when they land: `attackLook`, `SPELL_LOOKS`, `ABILITY_LOOKS`, `impactMs`, which the schedule holds later events for and the sounds time their outcome by; the floating text of an attack's on-hit damage, `bonusText`, and `changesStatusMarks`, which events redraw the nameplates' status letters), `boardGeometry.ts` (hex ↔ screen, for a `BoardLayout`: the battlefield's is squashed to look like a floor, the world map's is flat with smaller hexes), `attackPlan.ts` (what clicking a foe does, and the hint when it does nothing), `battleSetup.ts` (which encounter and threat a `Battle` start asks for: a monster location's, or else the data's; the seed a battle's log started with, which seeds the runes a win finds, and the names the victory screen's "Found:" line lists), `scrollingLog.ts`, `slotScroll.ts` (which rows of the ground pile the inventory shows), `gearDrag.ts` (where an item dragged in the inventory may be dropped and which change of gear a drop makes), `mapScroll.ts` (where the world map sits on screen for the party to be in view or as a drag panned it, and when a press has moved far enough to be a drag), `partyPanel.ts` (where the party's portraits sit and what a click on one does), `draftInfo.ts` (the lines a hover shows of a draft), `encampmentView.ts` (where the encampment screen draws each facility, and with which frame of its sprite), `gearCompare.ts` (the stat sheet's wards, `wardsLines`, wrapped onto indented rows to fit each tab's column; the character panel's warning when the weapon's attack costs more AP than a turn gives, `attackCostWarning`, in the panel's amber and `attackWarning` in its probe; the trading post's and crafting screen's words for an item's stats and what a craft changes, attacks a turn included, with the strength an item asks and, where a wearer is known, the shortfall's cost, and the AP, reach, ranged-piercing, spell-skill, mana, wards, Max HP and on-hit lines, every on-hit entry on the one line; the trading post knows no wearer and shows the bare requirement), `runecraftView.ts` (the crafting screen's Runes tab in words: an item's sockets, the pouch's lines, a rune's effect in each place, and each action's id, preview, refusal and message, from runecraft.ts; and where sockets come from, `socketSources`, which the empty list's hint and a rune's "Set in a socketed item" line at the trading post and in the pouch say), `worldEvents.ts` (the world map's words for what a turn brought), `hexInfo.ts` (what the world map's info panel tells of the hovered hex, only what the fog lets the player know), `partyList.ts` (the parties the world map lists and where their entries sit; `deployedParties` is the only reader of the single party, which stage 05 turns into several), `perkTree.ts` (where the nodes of the perk tree and the spell tree sit, built from the perks' own `branch`, `requires` and `school`, and how each stands for a character or, in creation, for a draft), `spellMenu.ts` (the battle's spell list and the words of aiming a spell), `foeInfo.ts` (the lines the battle's hover panel shows of a foe: its name, each ability with when it is next usable, counted in the foe's turns, and what it does, worked out from the ability's data, `STATUSES` and the foe's `abilityDamageBonus`, so a new ability is described for free; then its wards), `clicks.ts` (what counts as a right-click), `sounds.ts` (which sounds an event triggers), `audioSettings.ts` (volume levels, saved to `localStorage`), `cursors.ts` (the pointer cursors, as inline SVG), `seed.ts` (the seed in the page's address), `debugCommands.ts` (the debug console's commands), `unitLook.ts` (the names of the sprite atlas's frames, animations and points, and which sprites are laid under and over a hero's body for what it wears and holds). Six helpers do import Phaser, each the game objects of something a scene or several draw, with no logic of its own: `PartyColumn.ts` (the party's column, shared by the three scenes that show it, its colours and `hpBarColor` in `partyPanel.ts`), `PartyListView.ts` (the world map's party list), `UnitFigure.ts` (a unit's body with what it wears and holds drawn under and over it, animated as one: the battle's units, the world map's party and the character panel's doll), `PerkTreeView.ts` (a tree's nodes, lines and strip, the perk tree's or the spell tree's, a spell's node edged in its school's colour, drawn by the character panel and by creation, each of which says what a click on a node does), `socketPips.ts` (an item's socket pips under its icon, which takes Phaser's types only) and `panelButton.ts` (the framed button of the party screen and creation, drawn faint but clickable when `dimmed`, and `fitText`, which cuts a list line's name short with an ellipsis).

A scene that redraws itself after a change (`Inventory`, `Party`, `Creation`) does so on the next tick, as the redraw destroys the button whose click handler asked for it, and its new buttons take clicks only from the frame after.

Every scene but `Boot` has a `probe()`: plain data telling where its controls are on screen and what state it shows, typed in `src/testHook.ts`. In dev builds `main.ts` installs the hook that puts the probes within the in-browser tests' reach as `window.__yomi`; a production build leaves it out. Game code must not read the hook or the probes. A control that a test needs to click goes in its scene's probe.

### Tests

`vitest.config.ts` defines two projects, and where a test file lives decides how it runs:

- `domain` (Node environment): every `*.test.ts` under `src/` and `scripts/` except the ones below. Helper modules in `src/scenes/` must stay free of runtime Phaser imports for their tests to run here.
- `scenes` (jsdom + canvas mock, shared module graph): only `src/scenes/*Scene.test.ts`. These are smoke tests; real behaviour is tested through the helper modules and the engine.

Tests that need determinism pass a seeded `mulberry32` or a scripted RNG into the engine.

The in-browser tests in `e2e/` are a separate run (`npm run test:browser`, with its own `vitest.browser.config.ts`) and not part of `npm test`: they take seconds each and need Playwright's Chromium, which the podman image carries for `make test-browser`. They play the real game served by a Vite dev server and check what the others cannot: the scenes handing over to each other, overlays pausing and resuming, assets loading, layout on resize. Run them after a change to a scene. `e2e/CLAUDE.md` says how they work and how to add one.

### Assets and docs

Sprites in `public/assets/sprites/` are generated from `art/` (see Sprites) and audio in `public/assets/audio/` is placeholder; each directory's `README.md` records provenance and licence and should be updated when files are added. `BootScene` preloads every sound in `SOUND_KEYS` (`sounds.ts`; `BattleScene` and `WorldScene` each loop a theme of their own, `music_battle` and `music_world_map`, paused while the menu is over them) and the sprite atlas with its animations (`atlas.png`, `atlas.json`, `atlas.anims.json`), from which everything that moves is shown: units, what they hold and the world map's locations. A frame is named `<sprite>/<frame>` and an animation `<sprite>/<anim>` (`spriteFrame`, `spriteAnim`), and the animations themselves are written in the sprites' sources, not in the scenes. A unit is drawn as the atlas's sprite named for its `UnitKind`, with `idle` and `walk` animations, so a new unit kind needs a sprite of that name with both and an experience value in `FOE_XP`. Every hero is the `warrior` body, bare, with sprites laid under and over it for what it wears (`WORN_SPRITES`, and `WORN_BACK_SPRITES` for the cloak's cape behind it) and holds (`GEAR_SPRITES`), all in `unitLook.ts` by the item's icon, from `art/gear/`, and drawn in `heroLook`'s order (cape, body, armour, cloak, head, main hand, off hand, whichever way it faces); an item whose icon has none is worn or held unseen, so a new weapon or shield icon, or armour, head or cloak icon, needs an entry there and a sprite, or `unitLook.test.ts` fails; `BattleScene` puts a hero's gear on its figure again whenever the character panel closes. A strike's lunge, a hit's flash and the battle's other effects are tweens in `BattleScene`, as they were never frames: a blade or axe swung about the fist (`UnitFigure.swing`, the sprites in `SWUNG_GEAR`, turned about the body's `grip` point, which the atlas carries on each frame as Phaser's `customData` and `pointFromAnchor` reads), a slash, arrows and wand bolts in flight, each spell's missile and impact (as `battleEffects.ts` picks; an arrow, a missile and a burst are sprites of the atlas from `art/effects/`, turned along their flight about their `tip`, a missile and a burst tinted in the spell's colour, while flares, trails, clouds, motes and rings are drawn shapes), shots and spells aimed at and flying from each unit's `chest` point, a hit's knock or a miss's dodge, a step's bob, and an outline pulsed on whoever a blow or a spell lands on (`UnitFigure.pulseOutline`, Phaser's Glow filter, drawn only by WebGL). `InventoryScene`, `TradingPostScene` and `CraftingScene` load one icon per `ItemIcon` from `assets/sprites/icon_<icon>.png`, keyed by `ITEM_ICON_KEYS`, and also every rune's icon and the two socket pips (`RUNE_ICON_KEYS`, `SOCKET_PIP_KEYS`; `RUNE_COLOURS` tints a filled pip, and `socketPips` and `pipOffsets` say which pips an item shows and where, drawn under its icon by `socketPips.ts`'s `createPips`, which `InventoryScene` uses in its slots, backpack and ground and `TradingPostScene` and `CraftingScene` in their lists) (`itemIcons.ts`, which also has the pale tint a tier-2 material lays over its family's icon, `MATERIAL_TINTS` and `iconTint`, which the three scenes apply to every item icon they draw). `WorldScene` shows one atlas sprite per `LocationKind`, keyed by `LOCATION_SPRITES`, `map_watchtower` for a tower and `map_blight` on each corrupted hex, each playing its `idle`, and shows the party as its first member's battle figure, dressed in what it wears and holds. `EncampmentScene` draws each facility from the atlas as `camp_<facility>/level_<n>` (by `FACILITY_SPRITES`), or `camp_plot` while it is not built, on the 48px `building` canvas, with `camp_tent` and `camp_fire` for the look of the place. Every scene with a `PartyColumn`, and `Party` and `Creation`, loads one portrait per `PortraitId` from `assets/sprites/portrait_<id>.png` (`portraitKey`), so a new preset needs an id in `PORTRAIT_IDS` and a matching sprite in `art/portraits/`.

`docs/manual/README.md` is the player's manual, which the game shows from its menu (its images bundled from `docs/manual/images/`), its screenshots taken by `e2e/manual.shots.ts` (`vitest.manual.config.ts`, not part of either test run); a change to a rule it states or a screen it shows should update it and retake them. `docs/designs/` holds feature designs, written before a feature is planned: what to build and why, which may be ahead of the code. `docs/implementation-plans/` holds step-by-step plans with completion logs, which are useful for the reasoning behind past fixes.

### Sprites

Sprites are generated from text sources in `art/` with sprite-tool. `art/CLAUDE.md` has the workflow, and loads by itself when you work on files there; read it before drawing or changing a sprite. Never edit an exported PNG by hand: change the source and run `npm run sprites`.

## Keeping this file current

This file is the project's code map, and it is only worth loading if it is true. Update it in the same commit as the change that makes it wrong or incomplete; do not leave it for a later pass.

A change needs an edit here when it:

- adds, removes or renames a scene, or changes how scenes hand over to each other
- adds a domain module, or a helper module in `src/scenes/`
- adds or changes a command, npm script or simulator flag
- adds or changes a rule of play that someone would need to know before touching the code that enforces it
- adds a table that maps ids to assets (like `GEAR_SPRITES` or `ITEM_ICON_KEYS`), or changes which scene loads what
- changes how tests are split between the vitest projects
- makes a "not yet" statement here false (for example "there is no line of sight yet")

Before committing, search this file for every name the change renamed or deleted, and fix or remove the lines that mention it.

What belongs here is what the code does not say for itself: where a kind of logic goes, the contract between modules, the rules that span files, and the reason behind a constraint. Give a module one line on what it is responsible for, not a list of its exports. Leave out anything a grep answers, and do not grow a file-by-file inventory.

Keep this file to what most tasks need. Detail that matters only inside one directory goes in a `CLAUDE.md` in that directory, as `art/CLAUDE.md` does for sprites, with a one-line pointer here.
